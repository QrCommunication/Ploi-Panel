# Préparer une publication Google Play — Ploi Panel 0.1.0

**Checklist manuelle, pas une preuve de publication.** Le dépôt ne contient ni clé de signature ni configuration secrète. La publication exige accès administrateur Play Console, vérifications sur appareils et approbation humaine. Le package figé dans `app/build.gradle.kts` est `com.qrcommunication.ploipanel`, `versionCode = 1`, `versionName = "0.1.0"`, `minSdk = 29`, `targetSdk = 36`. Confirmer ces valeurs dans l'AAB avant envoi ; incrémenter `versionCode` pour toute version Play ultérieure. Vérifier les exigences Play actuelles lors de la soumission.

## 1. Préparer le compte et le package

1. Vérifier l'identité du compte développeur et la disponibilité/éligibilité du nom `com.qrcommunication.ploipanel` dans Play Console ; ne pas supposer qu'il est réservé parce qu'il apparaît dans le code. Dans **Android developer verification → Package names**, vérifier l'enregistrement, automatique ou manuel selon le cas. Pour les apps Play, l'[enregistrement des packages](https://support.google.com/googleplay/android-developer/answer/16984799) est requis à partir du **30 septembre 2026**. Pour une diffusion hors Play, consulter la [procédure de vérification Android](https://support.google.com/googleplay/android-developer/answer/16761053) : nouveau package = certificat public de signature ; package existant = preuve de possession de la clé, potentiellement APK signé avec snippet fourni par Google. Ne pas confondre cet APK de vérification avec l'AAB de publication.
2. Créer l'application dans Play Console avec nom, catégorie et coordonnées vérifiées. Choisir les pays, accès et mode de test ; respecter les éventuels critères de tests fermés et d'éligibilité propres au compte. Ne pas annoncer de disponibilité publique avant confirmation dans la console.

## 2. Signature et artefacts

1. Choisir **Play App Signing** pour une nouvelle application. Google signe les APK distribués avec la **clé de signature de l'application** ; le développeur signe l'AAB soumis avec une **clé d'upload distincte**. Pour cette release, une clé d'upload RSA 4096 bits PKCS#12 a été créée localement sur la machine de build : `/home/ploi/.local/share/ploi-panel/keys/upload-key.p12` (alias `ploi-panel-upload`). Ses mots de passe et sa configuration privée sont dans `/home/ploi/.local/share/ploi-panel/keys/upload-signing.properties` (accès propriétaire uniquement). **Sauvegarder les deux fichiers dans un coffre chiffré hors de cette machine avant l'enrôlement Play** ; ne jamais les committer ni les téléverser sur GitHub, Play Console ou une issue. La perte de l'upload key nécessite une procédure de réinitialisation auprès de Google. Référence : [Play App Signing](https://support.google.com/googleplay/android-developer/answer/9842756).
2. Le **certificat public** est `/home/ploi/.local/share/ploi-panel/keys/upload_certificate.pem`, également joint à la release GitHub. Empreintes vérifiées sur l'APK signé :
   - SHA-256 : `B7:30:6E:D9:1B:D2:6A:A1:D2:A8:A9:BA:53:6E:13:9B:10:28:F1:9D:D9:57:9C:06:CB:33:58:2F:F6:D9:CE:E3`
   - SHA-1 : `2C:F9:F5:B8:59:C1:DE:A1:FF:B6:FB:50:10:38:A9:87:74:00:DE:37`
   Vérifier dans **Play Console → Intégrité de l'application → Signature de l'application** quelle empreinte correspond à la **clé d'upload** et quelle autre à la **clé de signature Play**. Ne jamais téléverser le keystore privé ni partager ses mots de passe. Les empreintes et le PEM ne sont pas des secrets.
3. La configuration Gradle lit uniquement le fichier privé indiqué par `PLOI_PANEL_SIGNING_PROPERTIES` ; `assembleRelease`/`bundleRelease` échouent si la variable manque. Pour reproduire une build sur **une autre machine**, restaurer le keystore depuis le coffre et créer localement un fichier propriétaire (`chmod 600`) contenant `storeFile=/chemin/absolu/upload-key.p12`, `storePassword=…`, `keyAlias=ploi-panel-upload`, `keyPassword=…` ; ne jamais committer ce fichier. Sur la machine de build autorisée :
   ```sh
   export PLOI_PANEL_SIGNING_PROPERTIES=/home/ploi/.local/share/ploi-panel/keys/upload-signing.properties
   ./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleRelease :app:bundleRelease
   "$ANDROID_HOME/build-tools/35.0.0/apksigner" verify --verbose --print-certs app/build/outputs/apk/release/app-release.apk
   keytool -printcert -jarfile app/build/outputs/bundle/release/app-release.aab
   ```
   Contrôler que **les deux empreintes de signature coïncident avec celles ci-dessus**, ainsi que le package/version via `aapt dump badging` ou `bundletool`. Le certificat auto-signé est normal pour une clé d'upload Android : `jarsigner -verify -strict` émet des avertissements de chaîne de confiance/timestamp sur les AAB, ce n'est pas un contrôle Play et **ne valide pas** l'installation. Les APK Play générés depuis l'AAB seront signés par la clé d'application Google et peuvent ne pas mettre à jour un APK GitHub signé autrement.
4. Pour une **nouvelle app Play**, publier un **Android App Bundle (.aab)**, pas seulement un APK : [exigence AAB](https://support.google.com/googleplay/android-developer/answer/9844679). Tester une installation Play (piste interne/fermée) et les mises à jour sous la signature Play. La diffusion directe d'un APK impose son propre modèle de signature et de mises à jour.

## 3. Fiche, conformité et test

- Rédiger fiche FR/EN honnête : gestion de serveurs/sites Ploi par jeton personnel, widgets et checks locaux best effort ; **pas** de terminal SSH, d'OCR, de fréquence d'alerte garantie, ni d'affiliation officielle Ploi. Fournir icône, captures réelles téléphone et tablette/pliable si revendiqués, bannière et coordonnées de contact ; aucun jeton, IP privée, nom de client ou donnée réelle dans les captures. Les captures et visuels restent à produire manuellement.
- Héberger une URL publique stable pour la [politique de confidentialité](PRIVACY.md) et renseigner les formulaires Play **Data safety**, accès à l'application, audience, contenu, publicité et déclarations de permissions selon le comportement réellement observé et les règles en vigueur. `INTERNET` et `POST_NOTIFICATIONS` sont déclarées ; l'alerte est facultative et la permission demandée à l'activation sur Android 13+. Documenter le trafic vers Ploi et les sites contrôlés, sans prétendre « zéro transfert de données ». Vérifier que l'export utilisateur et l'exclusion des sauvegardes Android sont correctement décrits. Revoir dépendances et SDK avant déclarations définitives.
- Tester sur API 29 à 36 et appareils/lanceurs pertinents : onboarding PIN/biométrie, profil à droits limités, 401/403/429/offline, erreurs API et actions sensibles **sur ressources de test autorisées**, notification autorisée/refusée, mise en veille, widgets 1/4 serveurs et sites, verrouillage, restauration d'archive sur autre appareil, mise à jour APK vs Play. Aucun test destructeur sur serveur de production. Conserver résultats et anomalies ; les tests JVM/lint ne remplacent pas ces essais.
- Charger l'AAB signé sur une **piste de test interne**, traiter les avertissements Play (Android vitals, compatibilité, policy), puis test fermé/ouvert et production seulement après validation humaine. Vérifier dans Play Console la version et le certificat réellement servis, et le statut de publication effectif. En cas de rejet, corriger et réévaluer les déclarations plutôt que de promettre une date.

Voir [README](../README.md), [confidentialité](PRIVACY.md), [sécurité](../SECURITY.md). Ces étapes n'impliquent aucun téléchargement ni publication automatique depuis le dépôt.
